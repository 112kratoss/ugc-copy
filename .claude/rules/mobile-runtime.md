# Mobile runtime gotchas

Moved unchanged from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here.

- **Mobile runtime gotchas**: sheets and dialogs with text inputs render through `ugc-mobile/components/overlay-host.tsx`, not RN `Modal`. On Android a `Modal` is a window of its own and the keyboard tracker reads nothing in it; the most that arrived there on the Pixel 9a emulator was React Native's own event, after the keyboard had stopped moving and 24dp short. `ugc-mobile/__tests__/hig-modality.test.ts` fails any Modal that holds a field: the Reference details sheet, the model picker and the post composer's resource editor were the last three. A sheet moved to the overlay host owns what the Modal gave it: its entrance and exit (`useSheetPresentation` and `sheetMotion` in `components/sheet-chrome.tsx`), Android's back key (`useHardwareBack`), and putting away the keyboard of the page it opens over. It has to give up height to the keyboard as well as follow it: a panel with a height in points needs `flexShrink: 1` inside an area that stops under the status bar, or it is lifted whole and its title and Close button leave the top of the screen, as the resource editor's did. Its slide is drawn on the main thread, where a Modal's is the system's: a video player built with the sheet took the first 32 to 197 ms out of a 300 ms entrance on both platforms, so build one once `useSheetPresentation` says `onEntered` (`MediaPreview`'s `playerHeld` draws the clip's frame until then). The hook starts every slide only once the panel has been laid out, from a place below the screen, so rows and fields built with a sheet delay its start (the model picker's sixteen rows: about 70 ms on the emulator) instead of taking its first frames. The sheet's `KeyboardAvoidingArea` takes `followsKeyboard={presentation.settled}`: a keyboard is leaving whenever a sheet opens over the page's keys or closes with its own up, and an area that follows it moves and resizes the sheet under its slide (on the emulator a sheet opened over a keyboard came into view part-way up, sank and rose again); `__tests__/keyboard-avoidance-coverage.test.ts` fails a hosted sheet's area without it. An `Animated.Value` that a native animation will drive is made with `{ useNativeDriver: true }`, as the hook's are: until its first native animation a value is changed from JS, on Fabric that reaches the view through `setNativeProps`, and the view's shadow node applies those props again at every later layout, over what the native driver has drawn since (`ShadowNode::clone`, `nativeProps_DEPRECATED`). The first sheet a screen opened sat at its first offset for as long as it was being laid out anew, then jumped to rest. Run the pinned local Expo CLI (`./node_modules/.bin/expo`, as `.claude/launch.json` does) — `npx expo` against an empty `.bin` silently downloads a different major. Home's For You first page is kept on the device between launches (`ugc-mobile/lib/persisted-home-feed.ts`) and restored from the root layout, so a cold start draws the last posts while the feed refreshes: anything that clears the persisted Supabase session must also call `clearPersistedHomeFeed()`, and `__tests__/persisted-home-feed.test.ts` fails when the two calls stop pairing up.
- **A player with native controls answers its own touches (Android)**: expo-video's view tells JS when a touch on it begins and, for a touch on the seek bar, never that it ended. So nothing in JS may hold a touch that begins on such a player: a holder has Android cancel the player's buttons at the finger's first movement, is never let go after a touch on the seek bar, and then swallows the next press: inside an RN `Modal` the Modal's own host did, and on a page the scroll view did while the keyboard was up. The player's view stops the responder question at itself (`ugc-mobile/lib/native-touch-owner.ts`), and anything above a player that takes a *moving* touch, as a sheet's drag does, asks `touchBelongsToNativeView` first. `adb shell input tap` sends no move event and passes every one of these faults: press with `adb shell input swipe x y x y 120`, then press the neighbouring controls and the gesture after. `ugc-mobile/__tests__/native-touch-owner-responder.test.tsx` runs React Native's own renderer over a stand-in native side (`__tests__/mocks/react-native-responder-host.ts`), which is how a unit test can ask who is left holding a touch. One holder JS cannot get in ahead of: a view that takes the start question in the capture phase, as a `ScrollView` does while it is coasting from a fling, or at the default `keyboardShouldPersistTaps` while the keyboard is up. Ending that takes the native fix, which has the view go on reporting such a touch: it is parked in `ugc-mobile/experiments/android-video-view-touch-end/` until the next Android store build, and `ugc-mobile/__tests__/android-video-view-touch-end.test.ts` fails the release bump that leaves it there.
- **One dev-launcher load at a time (iOS)**: a second load started while the first is still fetching its manifest (a tap on a server row, or `simctl openurl` straight after `simctl launch`) makes the dev client build two React instances at once, and it can die in `NotificationCenterManager.addDelegate` before any JS runs. That is expo-notifications 55 keeping its delegate list without a lock ([expo/expo#49554](https://github.com/expo/expo/pull/49554)), not the change under test: launch once, then wait for the app's own UI, or for the launcher's "Failed to connect" alert, before starting another load. The fix is parked in `ugc-mobile/experiments/ios-notification-delegates-lock/` until the next iOS store build, and `ugc-mobile/__tests__/ios-notification-delegates-lock.test.ts` fails the release bump that leaves it there.
- **On Android expo-video's fullscreen player is a second activity**: while it is in front the app's own activity is paused, so `AppState` reads `background` for every listener in the app, JS timers do not fire, and nothing tells JS if the app is then left from there. `ugc-mobile/lib/use-native-preview-playback.ts` is where a preview clip tells that from the app going away, and what expo-video does and does not stop by itself is written there.
- **Mobile bundle shaping** lives in `ugc-mobile/bundler/`, wired through `babel.config.js` and `metro.config.js`: lucide icons are rewritten to one import per icon module (the package root is a barrel over ~1,700 icons), and iOS/Android bundles get a stand-in for RevenueCat's browser implementation. Fonts count too, since every font a bundle requires ships inside the binary. On Android, Metro resolves Expo Router's NativeTabs icon converter to its other-platform version, which keeps expo-symbols' seven Material Symbols weights (~3 MB) out. Google fonts are imported one weight per module (`@expo-google-fonts/<family>/<weight>`, with `useFonts` from `expo-font`). `__tests__/bundle-shaping.test.ts` guards all of it. Metro's transform cache does not track the Babel plugin, so run `expo start --clear` after editing it. Measure bundle composition from `expo export --source-maps`, never with `EXPO_ATLAS=1` — it installs `expo-atlas` into `package.json`, a fingerprint input. Metro also **inlines requires** (Expo ships it off): a module evaluates when one of its bindings is first used, not when its importer loads, so a module-scope side effect (registering a handler, a listener) in a lazily used module runs late. `app/_layout.tsx` is exempt and loads eagerly — install anything that must exist at launch from there.
- **On Android a `Modal` is a second window, and `AppState` `blur` speaks only of the activity's**: React Native emits `blur` when the activity's window loses the focus and `focus` when it has it back. The notification shade does that, and so does every RN `Modal` (a dialog) as it opens and closes; a dialog's own focus reaches JS as nothing at all, so the shade pulled over an open Modal is no event. Preview clips pause on `blur` (`ugc-mobile/lib/use-native-preview-playback.ts`): it is what stops a clip on the page when a Modal comes over it, and it paused the lightbox's own clip as the lightbox opened, until what the lightbox draws was wrapped in `ModalWindowScope` (`ugc-mobile/lib/modal-window.tsx`). A Modal that mounts a clip meant to play as it opens needs the same wrap, and anything new that reads `blur` as "covered" asks `useInModalWindow` first. expo-video's fullscreen player is another activity: that is `AppState` `change` to `background`, with a `blur` after it.
- **React Compiler** is switched on in `ugc-mobile/babel.config.js` for `app/`, `components/` and `lib/` — never through `experiments.reactCompiler` in `app.json`, which feeds the OTA runtime fingerprint and would strand every installed build. It skips, rather than breaks, any function that breaks the Rules of React: a ref read or written during render, `try…finally`, or (with `validateNoImpureFunctionsInRender`) a call like `Date.now()` during render, whose first result a memoized render would keep. A skipped function just loses the memoization; `'use no memo'` opts one out by hand.
- **On Android every Expo async function starts on one thread**: expo-modules-core runs each `AsyncFunction` without its own queue, `Coroutine` bodies included, on a single `HandlerThread` (`expo.modules.AsyncFunctionQueue`, `expo-modules-core/android/.../kotlin/AppContext.kt`), and a coroutine leaves it only at its first suspension. A call that blocks before then (a network open, a disk read, a decode) holds every other module's async calls: SecureStore's session reads, haptics, the clipboard, the viewer's `replaceAsync`. A JS deadline cannot free that thread. Stock expo-video 55's `generateThumbnailsAsync` opens a remote clip there: on the Pixel 9a emulator a link that sent nothing for 20 s kept a SecureStore read and a haptic waiting 31 to 40 s. Before calling an Expo async function on Android, read its Kotlin for work done ahead of the first suspension. The fix for the stills (`generateThumbnailFromUrlAsync` on `Dispatchers.IO`) is parked in `ugc-mobile/experiments/android-remote-video-still/` until the next Android store build, `ugc-mobile/__tests__/android-remote-video-still.test.ts` fails the release bump that leaves it there, and `ugc-mobile/lib/video-frame.ts` reads stills on Android only where the binary has that function.
- **Leaving the app from Android's fullscreen player does not stop a clip that is still waiting for data**: expo-video's fullscreen activity stops a clip on the way out only if it is playing at that moment, so one that has been asked to play and has no data yet starts when the data comes, behind the launcher or the lock screen. JS cannot see that leaving at all: the app's own activity is already paused under the fullscreen player, so `AppState` says nothing and no timer runs. The native fix (the activity asks whether the clip means to play, `playWhenReady`) is parked in `ugc-mobile/experiments/android-fullscreen-waiting-clip/` until the next Android store build, and `ugc-mobile/__tests__/android-fullscreen-waiting-clip.test.ts` fails the release bump that leaves it there. That folder's README says what `ugc-mobile/lib/use-native-preview-playback.ts` can drop once updates reach only builds that carry it.
