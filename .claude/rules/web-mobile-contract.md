# Web ↔ mobile contract

Moved unchanged from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here.

`contracts/` holds sixteen versioned JSON contracts. Five are consumed **at runtime**: `mobile-api-operations-v1.json` by `src/proxy.ts` (Next middleware) to build the mobile CORS allowlist, `universal-links-v1.json` by `src/lib/app-links.ts`, `post-resource-bundle-authoring-v1.json` by `src/lib/post-composer-resource-cards.ts`, `credit-packs-v1.json` by `src/lib/pricing.ts` (the packs the web sells and `mobile-commerce.ts` maps store products to), and `reserved-handles-v1.json` by `src/lib/profile.ts`. Metro cannot load a file from outside the app, so the mobile side carries copies of those last two (`ugc-mobile/lib/pricing.ts`, `ugc-mobile/lib/edit-profile-form.ts`) that `credit-packs-contract.test.ts` and `edit-profile-form.test.ts` hold equal to the contract. `proxy.ts` also enforces mobile client version gating (HTTP 426 with upgrade policy, `/api/app-version` exempt). The other eleven (`mobile-api-v1.json`, `generation-model-catalog-v1.json`, `model-catalog-transport-v1.json`, `model-catalog-subjects-mode-v1.json`, `template-run-media-v1.json`, `upload-queue-contract-v1.json`, `hide-creator-label-v1.json`, `feed-recipe-chip-v1.json`, `whats-new-models-v1.json`, `production-motion-descriptors-v1.json`, `public-post-quality-v1.json`) are shared test fixtures imported by both `src/__tests__` and `ugc-mobile/__tests__`, so a breaking API change fails tests on both sides (`hide-creator-label`, `feed-recipe-chip` and `whats-new-models` hold the web and the app to one answer each: the wording of the row that hides a creator, when a feed card names its recipe and in what words, and which catalog models count as new and in what order; `public-post-quality` holds the server's public-post rule (`getPublicPostQualityError`) and the app composer's check before step 2 says "Ready to publish" to the same cases, and lists the placeholder and filler words the shared `isPlaceholderText` reads (a title is refused only when it is made of nothing else: "Demo video" is, "Product demo" is not); `production-motion-descriptors` holds both creators to the motion slots production publishes, and `production-motion-descriptors-contract.test.ts` fails once a newer catalog release re-emits a motion model, when it is read from production again). Changing a mobile-facing route means updating the contract files and both test suites. Four source modules are also shared across the workspaces by relative import: `ugc-mobile/lib/model-catalog/protocol.ts` (transport types, validators, the condition evaluator, and the lists of control types, input modes, slot kinds and roles and constraint types both creators render), `ugc-mobile/lib/model-catalog/session.ts` (the paged client session) and `ugc-mobile/lib/model-catalog/seedance-assets.ts` (the Seedance 2 family's prepared-asset metadata, its readers, and the asset-id-over-link rule both creators apply when they build a run; `src/lib/seedance-assets.ts` re-exports it) and `ugc-mobile/lib/model-catalog/provider-prompt-limits.ts` (each model's Kie prompt limits: the server's starts refuse by them, through `src/lib/provider-input-limits.ts`, and both creators count against them while typing) — keep them free of React Native, Expo and Node imports, because the web bundle and the server compile them too. The catalog build may publish only what those lists name: `src/__tests__/model-catalog-client-parity.test.ts` holds the server to them and `ugc-mobile/__tests__/model-catalog-client-parity.test.ts` holds the native parser to them, so a capability reaches both creators or neither. Named subjects (several pictures fused into one `@handle`) were the gap that rule closed: the server built a `subjects` input mode only the web page could group, until the native creator learned the slot. That folder carries its own self-contained `tsconfig.json`: Vite resolves the nearest tsconfig for every file it transforms, and `ugc-mobile/tsconfig.json` extends `expo/tsconfig.base`, which the web workspace never installs, so without it the web test job fails on the CI runner with `TSCONFIG_ERROR … Tsconfig not found` while passing on any machine that has `ugc-mobile/node_modules`. Never add an `extends` to it. `.vercelignore` keeps the mobile workspace out of the Vercel upload except `ugc-mobile/lib`, which goes up whole (`ugc-mobile/*`, then `!ugc-mobile/lib`). `next build` type-checks the app against the upload, so even a file it reaches only with `import type` must be in it; a plain `ugc-mobile` entry once made the build fail with `Module not found` while every local build passed. `vercelignore-shared-catalog-modules.test.ts` pins those two lines and reads the rest from the code. Whatever the type-checked app reaches in the mobile workspace must sit in `ugc-mobile/lib`. That means imports, re-exports, `import()`, `require()` and `import type`, followed through every file reached. Every mobile file the web or its tests load at run time must also have a nearest `tsconfig.json` with no `extends`. So a new shared folder fails the test until it has that tsconfig, with no case of its own to add. A run-time import of a file directly in `ugc-mobile/lib` fails it too, because that file's nearest config is `ugc-mobile/tsconfig.json`. The post publish policy is shared the same way: `ugc-mobile/lib/post-publish-policy/post-publish-policy.ts` (the placeholder-title rule and the public-post rule built on it, `getPublicPostQualityError`, which `src/lib/marketplace-trust.ts` re-exports for the routes; the shortest title a Free or Paid recipe goes out under, `RECIPE_TITLE_MIN_LENGTH`, which the listing rule reads and `marketplace-trust.test.ts` holds to the database's, and whose refusal the create, publish and update routes send in plain words with `field: 'title'` and `code: 'RECIPE_TITLE_TOO_SHORT'` (pinned under each in `mobile-api-v1.json`), for both composers to answer with "Post without recipe" (owner, 2026-11-03); the title both composers suggest for a creation with none, from the prompt unless a paid recipe keeps it private (a free one may, owner 2026-10-29), and a remix's from its original's ("intense (remix)"); and the handle suggested to a creator who still has `creator-xxxxxxxx`) is imported by `src/lib/marketplace-trust.ts`, `src/lib/creation-post-title.ts`, `src/lib/public-identity.ts`, the search gates (`src/lib/showcase-seo.ts`, `src/lib/sitemap-entries.ts`, for the titles a suggestion can name) and the app's `lib/post-new-view-model.ts` and `lib/public-identity.ts`, with the same self-contained `tsconfig.json`; beside it, `handle-suggestion.ts` holds the creator-name step's handle (the first suggestion, a taken one swapped for `<handle>-NNN` at most three times, the handle following the display name until its field is focused), read by the web's `src/app/onboarding/` and the app's `app/onboarding.tsx` (through `lib/handle-suggestion.ts`). Each path is counted as an onboarding event's `step` (`invite_handoff_play_referrer`, `_paste_offered`, `_paste_used`, `_paste_not_invite`, `_paste_dismissed`), never with a code. Both suites spell the two strings out (`src/__tests__/invite-install-handoff.test.ts`, `ugc-mobile/__tests__/invite-install-handoff.test.ts`): a change of format strands the invites of every app already installed. A code a person types is one more file of that folder, `invite-typed-code.ts` (owner, 2026-11-11: "suppose we can give a unique code instead of the link"): every invite has, besides its link code, a six-character code drawn by the database from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (`referral_codes.short_code`, migration 20261111073612), which both Invite & Earn screens show with a Copy and put in the shared message; the sign-in pages' "Have an invite code?" The app sends its held visit's token with the code (`requestVariants.typedCode` in `mobile-api-v1.json`), lets the server decide, and saves the answer only once it has one, as an invite's, which a bundle from before typed codes can still read. An invite visit takes a six-character code too, for the binaries in stores, whose Invite & Earn sends a typed code to the invite landing (the answer's `code` is the one sent while that invite is kept); a shared link takes only the link code. Each client brings its own storage for the recents (`localStorage`, guarded for a private window; AsyncStorage), and both end them at sign-out: the app clears them there (`lib/auth.tsx`), and the web's list remembers the account that kept it (`src/app/search/search-history.ts`), since a web sign-out can happen on any page. The parameters, a filtered answer, the corrected and exact answers, the answer of a server from before them (`beforeFilters`: the app draws entities, switches and the notice only once an answer has carried them) and a marked cursor are pinned under `searchPublicContent` in `mobile-api-v1.json`. The typeahead's rules sit in the same folder, `search-typeahead.ts` (2026-11-13): the answer of `GET /api/search/suggest` and its caps (5 creators, 3 models and tools, 6 completions), which `src/lib/search-suggest.ts` re-exports for the server; the 140 ms pause a request waits for and what text is worth asking about (`searchTypeaheadQuery`); the sections and their order; what is drawn while an answer is on its way (`searchTypeaheadDrawn`: this text's answer, or until it lands the one before it, stale, with an entity kept only while the text still names it) and when the list is drawn at all (only with the focus, never once closed or committed for that text); how long an answer may be kept to draw again (30 seconds, one focus of the box) and how long a count stands before it is said (500 ms); when a press on a row counts (`placeSearchTypeaheadRows`, `isSearchTypeaheadPressAccepted`: only once the row has stood where it is for 250 ms, a list that has just come on show at once; the keys are not held) and which rows are drawn as not taking one yet (`searchTypeaheadUnsettledRows`: the rows a change moved or brought, never one that stayed); what a row does; how the highlight moves under the keys; and the words a screen reader is told. It is imported by the web's `src/components/search/use-search-typeahead.ts` and `SearchTypeaheadList.tsx` (the search page's box and the top bar's field) and by the app's `lib/use-search-typeahead.ts` and `components/search-typeahead-list.tsx`. The route is pinned under `suggestSearch` in `mobile-api-v1.json` and is an operation of `mobile-api-operations-v1.json` (`api.suggestSearch`); its answer to a visitor is the one publicly cached answer among the app's routes, so the proxy's CORS `Vary` and the route's `Vary: Authorization` must both reach the response, which `tests/e2e/search-typeahead.spec.ts` asks of the dev server through the real proxy and route.

Notification deep links are part of that contract. The app opens a notification's `deepLink` only when its route is on the list in `ugc-mobile/lib/notifications.ts` (`NOTIFICATION_ROUTE_PATTERNS`); any other link does nothing in the Alerts list and falls back to Alerts from a push, with no error on either side. So every link the server writes has a line under `endpoints.mobileNotifications.deepLinks` in `mobile-api-v1.json`: `mobile-notification-deep-links.test.ts` holds the server's builder to those lines, and `ugc-mobile/__tests__/notification-deep-links.test.ts` holds the app to opening each one. A new destination needs its line, its route on the app's list, and that JS in users' hands (an OTA) before the server sends it. The web Alerts page turns the same links into web routes in `src/lib/web-notification-links.ts`.

`src/proxy.ts` is also the bearer admission boundary for every policy-listed `/api` route (`src/lib/route-identity-policy.ts`): it verifies the JWT locally with `auth.getClaims()` (ES256 against the project's published JWKS, cached per instance; a symmetric-key project would fall back to a GoTrue call by itself) and then makes exactly one database round trip, the zero-argument `current_identity_admission()` RPC, which returns the lifecycle state, `created_at`, whether the account is banned and whether the token's session still exists. It never calls `auth.getUser()` — the GoTrue `/user` round trip was the slow, variable half of signed-in latency (~450 ms median, past 1.5 s at P95 in busy hours). Successful admission travels to the route as the 30-second HMAC assertion (`identity-admission-assertion.ts`); routes without one fall back to `server-auth-user.ts`, the single audited `auth.getUser()` boundary. The guest list keeps one rule, what credits fund or the identity owns, and since product decisions D4 and D6 (2026-10-15) it holds starting a run of a published template (`POST /api/templates/[id]/runs`, like the `/api/template-runs/*` actions after it; authoring, testing and publishing a template stay registered), restoring a creation into the editor (`GET /api/remix-source`, whose loader serves a guest only a generation of its own or of an identity linked to it and answers every other guest request, a missing generation included, 403 `REGISTRATION_REQUIRED` in the proxy's words, so remixing someone else's post stays an account's) and the identity's credit history (`GET /api/credits/history`). A path's policy covers every method, with two kinds of exception, asked per request (`routeIdentityPolicyForRequest`). The GET of a registered-only path listed in `GUEST_READABLE_REGISTERED_ROUTES` (today the comments thread under a post and a post's resource bundle) is admitted for a guest's token too. That read is served to a visitor who sends no token at all, and a guest's app sends its token with every request, so the path's question refused every guest what a signed-out visitor is given (the app's post page read "Comments are unavailable"); list a path there only when its GET handler asks for no one. A write listed by method and path in `GUEST_WRITABLE_REGISTERED_ROUTES` is answered as `guest` for the same reason: the onboarding events (`POST /api/onboarding/events`), both share counters (`POST /api/showcase/share`, `POST /api/profile/share`) and moderation reports (`POST /api/moderation/reports`, whose adapter takes a guest's report only of a generation the guest owns and answers every other one 403 `REGISTRATION_REQUIRED` itself). A guest's deletion of itself is listed there too (`DELETE /api/account`, product decision D5): the handler asks a guest for no fresh sign-in, having none to ask for, and deletes the guest identity and what it made through the account-deletion pipeline, while a guest already linked to an account is answered 409 `SESSION_MERGED` at the proxy; the path's other methods stay an account's. List a write there only when its handler takes a guest as its caller and never answers one 401, which the app reads as an ended session; `route-identity-policy.test.ts` sends each listed write as a guest. Every other write of a registered-only path still answers a guest 403 `REGISTRATION_REQUIRED` at the proxy. The lifecycle state is read before the session: an account being deleted gets 409 `ACCOUNT_DELETING` even on a revoked session, since a deletion revokes every session of the account before it answers, and answering its other devices 401 told them the account was intact. A NULL row (the auth user is gone) stays 401. Under the production monitor the proxy reports `proxy-identity`, `proxy-verify` and `proxy-lifecycle` timings that the showcase feed folds into its `Server-Timing`.

Two routes own their admission instead (`route-owned-identity-admission.ts`,
whose list the proxy reads): the same evaluator runs at the actual route export,
the proxy strips incoming admission/timing headers and defers only the listed
methods of those exact paths, and every other path keeps proxy admission. For
`/api/showcase/feed` GET/HEAD it runs in `withRouteOwnedIdentityAdmission`, in
the API function's configured Mumbai region: the feed handler freshly verifies
claims, session, ban and lifecycle state before calling its adapter, then
supplies a new assertion for route reuse, and feed performance reports
`route-identity`, `route-verify`, `route-lifecycle` for this check. For
`/api/mcp` and its posting-only form `/api/mcp/posts` (every method) the MCP adapter runs it itself, because its refusals
differ from the proxy's: a missing or invalid token answers 401 with the
`WWW-Authenticate` challenge MCP clients start their OAuth flow from, and a
token without the agent claim (`agent-token.ts`) answers 403
`AGENT_TOKEN_REQUIRED`; the evaluator itself refuses an agent token on every
other `/api` route (403 `AGENT_TOKEN_NOT_ALLOWED`). Do not add a proxy exception
without wrapping and testing the real route export.
