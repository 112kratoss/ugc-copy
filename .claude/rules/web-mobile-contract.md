# Web ↔ mobile contract

Moved unchanged from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here.

`contracts/` holds sixteen versioned JSON contracts. Five are consumed **at runtime**: `mobile-api-operations-v1.json` by `src/proxy.ts` (Next middleware) to build the mobile CORS allowlist, `universal-links-v1.json` by `src/lib/app-links.ts`, `post-resource-bundle-authoring-v1.json` by `src/lib/post-composer-resource-cards.ts`, `credit-packs-v1.json` by `src/lib/pricing.ts` (the packs the web sells and `mobile-commerce.ts` maps store products to), and `reserved-handles-v1.json` by `src/lib/profile.ts`. Metro cannot load a file from outside the app, so the mobile side carries copies of those last two (`ugc-mobile/lib/pricing.ts`, `ugc-mobile/lib/edit-profile-form.ts`) that `credit-packs-contract.test.ts` and `edit-profile-form.test.ts` hold equal to the contract. `proxy.ts` also enforces mobile client version gating (HTTP 426 with upgrade policy, `/api/app-version` exempt). The other eleven (`mobile-api-v1.json`, `generation-model-catalog-v1.json`, `model-catalog-transport-v1.json`, `model-catalog-subjects-mode-v1.json`, `template-run-media-v1.json`, `upload-queue-contract-v1.json`, `hide-creator-label-v1.json`, `feed-recipe-chip-v1.json`, `whats-new-models-v1.json`, `production-motion-descriptors-v1.json`, `public-post-quality-v1.json`) are shared test fixtures imported by both `src/__tests__` and `ugc-mobile/__tests__`, so a breaking API change fails tests on both sides (`hide-creator-label`, `feed-recipe-chip` and `whats-new-models` hold the web and the app to one answer each: the wording of the row that hides a creator, when a feed card names its recipe and in what words, and which catalog models count as new and in what order; `public-post-quality` holds the server's public-post rule (`getPublicPostQualityError`) and the app composer's check before step 2 says "Ready to publish" to the same cases, and lists the placeholder and filler words the shared `isPlaceholderText` reads (a title is refused only when it is made of nothing else: "Demo video" is, "Product demo" is not); `production-motion-descriptors` holds both creators to the motion slots production publishes, and `production-motion-descriptors-contract.test.ts` fails once a newer catalog release re-emits a motion model, when it is read from production again). Changing a mobile-facing route means updating the contract files and both test suites. Four source modules are also shared across the workspaces by relative import: `ugc-mobile/lib/model-catalog/protocol.ts` (transport types, validators, the condition evaluator, and the lists of control types, input modes, slot kinds and roles and constraint types both creators render), `ugc-mobile/lib/model-catalog/session.ts` (the paged client session) and `ugc-mobile/lib/model-catalog/seedance-assets.ts` (the Seedance 2 family's prepared-asset metadata, its readers, and the asset-id-over-link rule both creators apply when they build a run; `src/lib/seedance-assets.ts` re-exports it) and `ugc-mobile/lib/model-catalog/provider-prompt-limits.ts` (each model's Kie prompt limits: the server's starts refuse by them, through `src/lib/provider-input-limits.ts`, and both creators count against them while typing) — keep them free of React Native, Expo and Node imports, because the web bundle and the server compile them too. The catalog build may publish only what those lists name: `src/__tests__/model-catalog-client-parity.test.ts` holds the server to them and `ugc-mobile/__tests__/model-catalog-client-parity.test.ts` holds the native parser to them, so a capability reaches both creators or neither. Named subjects (several pictures fused into one `@handle`) were the gap that rule closed: the server built a `subjects` input mode only the web page could group, until the native creator learned the slot. That folder carries its own self-contained `tsconfig.json`: Vite resolves the nearest tsconfig for every file it transforms, and `ugc-mobile/tsconfig.json` extends `expo/tsconfig.base`, which the web workspace never installs, so without it the web test job fails on the CI runner with `TSCONFIG_ERROR … Tsconfig not found` while passing on any machine that has `ugc-mobile/node_modules`. Never add an `extends` to it. `.vercelignore` keeps the mobile workspace out of the Vercel upload except `ugc-mobile/lib`, which goes up whole (`ugc-mobile/*`, then `!ugc-mobile/lib`). `next build` type-checks the app against the upload, so even a file it reaches only with `import type` must be in it; a plain `ugc-mobile` entry once made the build fail with `Module not found` while every local build passed. `vercelignore-shared-catalog-modules.test.ts` pins those two lines and reads the rest from the code. Whatever the type-checked app reaches in the mobile workspace must sit in `ugc-mobile/lib`. That means imports, re-exports, `import()`, `require()` and `import type`, followed through every file reached. Every mobile file the web or its tests load at run time must also have a nearest `tsconfig.json` with no `extends`. So a new shared folder fails the test until it has that tsconfig, with no case of its own to add. A run-time import of a file directly in `ugc-mobile/lib` fails it too, because that file's nearest config is `ugc-mobile/tsconfig.json`. The post publish policy is shared the same way: `ugc-mobile/lib/post-publish-policy/post-publish-policy.ts` (the placeholder-title rule and the public-post rule built on it, `getPublicPostQualityError`, which `src/lib/marketplace-trust.ts` re-exports for the routes; the title both composers suggest for a creation with none, from the prompt unless a paid recipe keeps it private (a free one may, owner 2026-10-29), and a remix's from its original's ("intense (remix)"); and the handle suggested to a creator who still has `creator-xxxxxxxx`) is imported by `src/lib/marketplace-trust.ts`, `src/lib/creation-post-title.ts`, `src/lib/public-identity.ts`, the search gates (`src/lib/showcase-seo.ts`, `src/lib/sitemap-entries.ts`, for the titles a suggestion can name) and the app's `lib/post-new-view-model.ts` and `lib/public-identity.ts`, with the same self-contained `tsconfig.json`. The saver notice's policy is shared the same way: `ugc-mobile/lib/saver-notice-policy/saver-notice-policy.ts` (the line both apps show at an account's first save, how long it stays, the per-account memory of having been told, and which request fields a save sends) is imported by `src/components/saver-notice.ts` and `ugc-mobile/lib/saver-notice.ts`, each of which only supplies its platform's storage, request and display. Its folder has the same self-contained `tsconfig.json` (no `extends`), pinned by the same test. The video and motion creators' settings chip is shared the same way: `ugc-mobile/lib/creator-settings-summary/creator-settings-summary.ts` (the chip's words, "720P · 16:9 · 5s" for a video run and "720P · 8s", or "720P · Add motion" until there is a clip, for a motion run) is imported by `src/app/create-video/CreateVideoClient.tsx`, `src/app/create-motion/CreateMotionClient.tsx` and the app's `lib/creator-parameter-summary.ts`, each of which only reads its own form or draft into it, with the same self-contained `tsconfig.json`, pinned by the same test; since 2026-10-28 a video chip names the run's sound on a model that can switch it ("480P · 9:16 · 5s · Sound off"), and the app's chip says so too once its next OTA ships. The creators' fitting rule is shared the same way: `ugc-mobile/lib/creator-run-fit/creator-run-fit.ts` (the settings a model opens on when a run moves to it, the model list split by what the balance covers, the model a remix opens on when the balance is short of the original, an option's price read against the balance, "Keeps your 2 references") is imported by the web creators and `src/lib/creator-video-candidates.ts`, with the same self-contained `tsconfig.json`, so the app can adopt the same rule; each side brings its own descriptors, form and quoted prices. How an unlocked recipe reads is shared the same way: `ugc-mobile/lib/recipe-reading/recipe-reading.ts` (what goes together, in which order and under which name: the creator's cards as they arranged them, then the rest by kind, Prompt, References, Settings, Notes, Workflow, Files, Links, with the creation's own references straight after the prompt that names them; inside a group its text first and its pictures, clips and sounds as one gallery; the line under a group's name, a locked card's line, a file's type in words, and the order "Includes …" counts in) is imported by `src/app/showcase/recipe-reading.ts` (the post page's panel, the reel and the buyer library), `src/lib/post-resource-bundles.ts` (the count order) and the app's `components/post-resource-bundle-content.tsx` and `lib/post-resource-bundle-view-model.ts`, with the same self-contained `tsconfig.json`; each client draws the groups it is given. Before 2026-10-29 each kept its own copy, and they drifted: the web listed everything outside a card under "More from this post", the app made a card per stored type. The creators price those lists with the batch quote route, `POST /api/generation-models/quotes` (at most `GENERATION_MODEL_QUOTE_BATCH_MAX` runs, in `protocol.ts`, each answered in its place), a guest route beside the single quote that reads no identity and counts a request once against a limit of its own (`generation-model:quote-batch`).

Notification deep links are part of that contract. The app opens a notification's `deepLink` only when its route is on the list in `ugc-mobile/lib/notifications.ts` (`NOTIFICATION_ROUTE_PATTERNS`); any other link does nothing in the Alerts list and falls back to Alerts from a push, with no error on either side. So every link the server writes has a line under `endpoints.mobileNotifications.deepLinks` in `mobile-api-v1.json`: `mobile-notification-deep-links.test.ts` holds the server's builder to those lines, and `ugc-mobile/__tests__/notification-deep-links.test.ts` holds the app to opening each one. A new destination needs its line, its route on the app's list, and that JS in users' hands (an OTA) before the server sends it. The web Alerts page turns the same links into web routes in `src/lib/web-notification-links.ts`.

`src/proxy.ts` is also the bearer admission boundary for every policy-listed `/api` route (`src/lib/route-identity-policy.ts`): it verifies the JWT locally with `auth.getClaims()` (ES256 against the project's published JWKS, cached per instance; a symmetric-key project would fall back to a GoTrue call by itself) and then makes exactly one database round trip, the zero-argument `current_identity_admission()` RPC, which returns the lifecycle state, `created_at`, whether the account is banned and whether the token's session still exists. It never calls `auth.getUser()` — the GoTrue `/user` round trip was the slow, variable half of signed-in latency (~450 ms median, past 1.5 s at P95 in busy hours). Successful admission travels to the route as the 30-second HMAC assertion (`identity-admission-assertion.ts`); routes without one fall back to `server-auth-user.ts`, the single audited `auth.getUser()` boundary. The guest list keeps one rule, what credits fund or the identity owns, and since product decisions D4 and D6 (2026-10-15) it holds starting a run of a published template (`POST /api/templates/[id]/runs`, like the `/api/template-runs/*` actions after it; authoring, testing and publishing a template stay registered), restoring a creation into the editor (`GET /api/remix-source`, whose loader serves a guest only a generation of its own or of an identity linked to it and answers every other guest request, a missing generation included, 403 `REGISTRATION_REQUIRED` in the proxy's words, so remixing someone else's post stays an account's) and the identity's credit history (`GET /api/credits/history`). A path's policy covers every method, with two kinds of exception, asked per request (`routeIdentityPolicyForRequest`). The GET of a registered-only path listed in `GUEST_READABLE_REGISTERED_ROUTES` (today the comments thread under a post and a post's resource bundle) is admitted for a guest's token too. That read is served to a visitor who sends no token at all, and a guest's app sends its token with every request, so the path's question refused every guest what a signed-out visitor is given (the app's post page read "Comments are unavailable"); list a path there only when its GET handler asks for no one. A write listed by method and path in `GUEST_WRITABLE_REGISTERED_ROUTES` is answered as `guest` for the same reason: the onboarding events (`POST /api/onboarding/events`), both share counters (`POST /api/showcase/share`, `POST /api/profile/share`) and moderation reports (`POST /api/moderation/reports`, whose adapter takes a guest's report only of a generation the guest owns and answers every other one 403 `REGISTRATION_REQUIRED` itself). A guest's deletion of itself is listed there too (`DELETE /api/account`, product decision D5): the handler asks a guest for no fresh sign-in, having none to ask for, and deletes the guest identity and what it made through the account-deletion pipeline, while a guest already linked to an account is answered 409 `SESSION_MERGED` at the proxy; the path's other methods stay an account's. List a write there only when its handler takes a guest as its caller and never answers one 401, which the app reads as an ended session; `route-identity-policy.test.ts` sends each listed write as a guest. Every other write of a registered-only path still answers a guest 403 `REGISTRATION_REQUIRED` at the proxy. The lifecycle state is read before the session: an account being deleted gets 409 `ACCOUNT_DELETING` even on a revoked session, since a deletion revokes every session of the account before it answers, and answering its other devices 401 told them the account was intact. A NULL row (the auth user is gone) stays 401. Under the production monitor the proxy reports `proxy-identity`, `proxy-verify` and `proxy-lifecycle` timings that the showcase feed folds into its `Server-Timing`.

For `/api/showcase/feed` GET/HEAD, the same admission evaluator now runs in
`withRegionalIdentityAdmission` at the actual route export, in the API function's
configured Mumbai region. The proxy strips incoming admission/timing headers
and defers only those two methods on that exact path; other paths keep proxy
admission. The feed handler freshly verifies claims, session, ban and lifecycle
state before calling its adapter, then supplies a new assertion for route reuse.
Feed performance reports `route-identity`, `route-verify`, `route-lifecycle` for
this check. Do not add a proxy exception without wrapping and testing the real
route export.
