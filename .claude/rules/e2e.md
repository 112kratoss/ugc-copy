# E2E (Playwright) gotchas

Moved from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here.

Five E2E gotchas worth knowing before you debug one:

- **Playwright's own dev server cannot start beside another `next dev` of the same checkout**, even on a different port: Next allows one per checkout (the server process holds `.next/dev/lock` while it runs; `lsof -t .next/dev/lock` prints its PID), and the second prints "Another next dev server is already running" with that PID among Playwright's `[WebServer]` lines, then Playwright fails with "Process from config.webServer was not able to start". Stop this checkout's preview/dev server (including one started via `preview_start`) before `npm run test:e2e`; the local gate's `--e2e` names it and skips. A `next dev` of another worktree has a `.next` of its own and does not matter. Port 3100 must be free as well: the config never reuses a server already on it.
- **The auth bypass needs its cookie, not just the env vars.** A spec that only visits an authenticated route lands on `/login`; add `{ name: 'e2e-auth', value: 'workflow-user', url: 'http://127.0.0.1:3100' }` via `context.addCookies` first (see the existing specs).
- **The dev server reloads an open page when another page connects after a compile.** `next dev --webpack` compiles a route the first time it is requested, and each compile gives the client build a new hash. Whenever any page opens its dev socket the server sends `sync`, with the current hash, to every open page, and a page that has had a `sync` before reloads itself when the new one carries another hash — Next takes the change for a server restart (`mostRecentCompilationHash` in `next/dist/client/dev/hot-reloader/app/web-socket.js`; the hot update itself applies fine). Two pages and one first request are enough: one Playwright worker's test compiles a route, the next page to load reloads the page under the other worker's test, and whatever that test had typed or attached in memory is gone. `playwright.config.ts` therefore runs the suite on one worker, in CI and out of it, which never has two pages open; a run given `--workers` above 1 still meets it, and so would a spec that opens two pages. A self-reload landing in the same tick as a spec's own navigation cancels it, surfacing as `net::ERR_ABORTED; maybe frame was detached?`. `tests/e2e/kling-o3-named-subjects.spec.ts` carries the retry helper for it. A page gets a second `sync` only when another page connects or its own socket reconnects, so a single page on one worker does not reload this way; the dev client can still reload a page after a failed hot update or a runtime error, and a trace shows any reload as a second load of the page's URL.
- **A compile spends the timeout of whatever is waiting while it runs.** The E2E server, `next dev --webpack`, compiles a route on its first request, and again after dropping it (`onDemandEntries`: unused for 60 seconds and not among the last five pages a browser has had open; it goes at the next compile). While any compile runs, every compiled route counts as building, so a request for any route waits for it, not only the first request for its own. A step with no timeout of its own absorbs the wait (`page.goto` and `page.request` calls, while the config sets neither `navigationTimeout` nor `actionTimeout`); a timed wait such as `expect`'s 10 seconds spends it. On CI's one worker `workflow-builder.spec.ts`'s redirect test failed this way: the redirect from `/create-workflow` loads `/login` as a new document, the suite's first request for that route, and its compile outlasted `toHaveURL`. That test now asks for `/login` with `page.request.get('/login', { timeout: 0 })` right before the wait, so the wait holds only the redirect; a `beforeAll` or `globalSetup` warm-up comes too early, because the route is dropped again before the test runs. Warm with `page.request`, not the `request` fixture: it shares the page's cookies (the proxy routes `/` and `/home` by them) and its trace (the fixture's own log takes `0-trace.network` and pushes the page's to `1-`). A wait that also covers a slow server render, which no warm-up shortens, keeps a named longer timeout, as `COLD_PAGE` and `SLOW_PAGE` do. In a failed test's trace, a document request with neither a response nor a failure when the wait ended was still being served (compiled or rendered); `[Fast Refresh] rebuilding` in the console marks a page compile's browser half, after its server half, and an API route's compile logs nothing; a request that failed with `net::ERR_ABORTED` was cancelled, and a second load of the starting URL is a reload.
- **A compile that ends while a page hydrates can hold the hydration until the dev server has rendered the page again.** After a compile that changes a seen route's server layer or its CSS imports, the server sends every open page `serverComponentChanges`, and the dev client answers with `hmrRefresh()` (with a reload instead after a runtime error). The client opens its HMR socket before `hydrateRoot` (`next/dist/client/app-index.js`), and the router's dispatch exists from the hydration render on, so the refresh can reach the router before it has mounted. Its tree waits for the page's refetch (`?_rsc=`) for its segments' data, and the hydration then renders that tree, because the router mounts with the refreshed state. So the page stays the server's HTML until the dev server answers: 6.7 to 7.6 seconds on CI. Every check that HTML satisfies passes meanwhile. A press there is dropped, because React stops a discrete event on a root it cannot hydrate. A fill never reaches React's state, and the field's next render after the commit writes over its text; the exceptions are the creators' prompt boxes and the post composer's fields, which take in what was typed as they mount (`useTypedBeforeHydration`, held by `creator-prompt-before-script.spec.ts` and `post-composer-typed-before-script.spec.ts`; the root layout's capture records inputs as well as textareas since 2026-11-06, never a password), and the fields of /login, /admin/login, /contact, /search, /templates, /pricing, /marketplace/sell and the video creator's Gemini Omni IDs, which take in whatever they hold as they mount (`useFieldValueBeforeHydration`, held by `login-typed-before-script.spec.ts`, the `contact-`, `search-` and `templates-typed-before-script.spec.ts` specs and the `pricing-currency-`, `seller-recipes-sort-` and `create-video-omni-id-before-script.spec.ts` specs; /contact's message takes only typing; the admin console's forms hand theirs over too, shown by a throwaway probe, as the E2E env cannot configure /admin; `field-hand-over-before-hydration.test.ts` asks every file that draws a controlled field for one of the two hooks, or a reason it need not). So a spec types or presses only after a sign that only the page's script gives. Since 2026-11-17 a signed-in creator's Generate shows the server's price for the run it opens on from the first paint, held, busy and named as being checked (`Generate · 19 credits · Checking the price`) until the page's own quote is in. So the signed-in creator specs (`creator-prices`, `creator-publish`, `creator-canvas`) type the prompt, which the prompt box takes in as it mounts, then wait for `Generate · 19 credits` to be enabled, which only the page's script does, once the page has hydrated and its own quote is in; by then the prompt box has taken in what was typed. On /create-video that is all it proves: Generate there takes a press with an empty prompt and refuses it in `handleGenerate`; `creator-signed-out.spec.ts` waits for the page's first quote request (it failed this way on 2026-10-31). A `__reactFiber$` key is not such a sign. It shows only that the render reached that node, and a refresh that lands after that leaves the key on HTML React has not committed, so the key checks of four specs narrow this window without closing it: the `hydrated()` helpers of `alerts-signed-out-sheet`, `pages-open-at-top` and `public-page-after-signed-in-route`, and the inline one in `bottom-nav-overlays`. Where a page gives no sign without a render of its own, React's record of the commit is one: `login-typed-before-script.spec.ts` waits until the document's root (its `__reactContainer$` key) no longer marks its tree dehydrated, which only the hydration's commit does, refresh or not. It stands for the form's commit only while no Suspense or Activity boundary sits between the root and the page: React hydrates each such boundary the server drew apart from the root, suspended or not, and Next wraps every segment in an Activity once `cacheComponents` is on, so a `loading.tsx` above a page or that flag ends the sign for it (`/admin/login`'s form already sits in a Suspense). In a trace, look for three things in order: the console's "Can't perform a React state update on a component that hasn't mounted yet", then two `?_rsc=` requests, then the page's mount-time requests (the model catalog, `/api/app-version`), which start only after those requests are answered.

## The dev server's env

`playwright.config.ts` is the only source of the dev server's env, in CI as on a laptop (the E2E job sets none): the placeholder project and keys (`PLACEHOLDER_ENV`), the shell's env without any variable `.env.example` lists, and no `.env*` file of the checkout. Next would apply every key of those files that the server's env leaves unset, at start and on every forced env reload, which it does when an env file is saved and when a route is added or removed (a branch switch in that checkout too; `forceReload` in `setup-dev-bundler.js`, which logs nothing unless a file's text changed). So the dev server's preload, `tests/e2e/support/dev-server.cjs`, first requires `no-env-files.cjs`, which answers Next's `fs.statSync` and `fs.readFileSync` of those files at the checkout's root as if they did not exist. `npm run test:e2e` is therefore the job's run from any checkout with nothing exported, and the primary checkout's `.env.local` (production) never reaches the server. `e2e-smoke-readiness.test.ts` holds all three: every `process.env` name the app's code reads is listed in `.env.example` (a new one must be, or the test fails), a shell exporting all of them reaches nothing, and Next's own loader, at start and on a forced reload, applies a checkout's four files without the guard and none with it, also when the guard was required by a path in another case (Next resolves its directory with `realpathSync.native`, and so does the guard). To change a variable for a run, change `PLACEHOLDER_ENV`. The server also starts on an empty data cache: the config's command removes `.next/dev/cache/fetch-cache` first, because the checkout's own `next dev` keeps `unstable_cache` entries there under keys that do not name the project (the primary checkout's held production's feed for the signed-out `/showcase` on 2026-10-23), and Next serves such an entry stale when its refresh fails, as every refresh against the placeholder does.

## The dev server's idle sockets

A spec's direct API read (`request.get`, `page.request.get`) goes through one keep-alive pool that the whole worker shares (`httpHappyEyeballsAgent` in `playwright-core/lib/server/utils/happyEyeballs.js`), so the socket one test's read left is the next test's first. Node's client agent honours a server's `Keep-Alive: timeout=5` only on an agent that has a timeout of its own (`keepSocketAlive` in `_http_agent.js`, the same in Node 22 and 24), and this one has none, so a pooled socket stays until the server closes it. `next dev` is a plain `http.createServer(listener)`, whose idle timeout of 5 s closes a socket 6 s after its last response (Node adds a buffer of 1 s). While a dev compile holds the server's event loop inside an I/O callback and the 6 s mark falls in it, the idle timer runs first when the loop turns and destroys the socket before the server has read the request already written to it, and the kernel resets the client: `apiRequestContext.get: read ECONNRESET`, with no line in the server's log. That failed `model-catalog-transport.spec.ts:173` and `creator-canvas.spec.ts:263` in eight Quality runs between 2026-11-17 and 2026-11-23, each time the first API read of the test, on the socket the test before it left; re-runs passed. (The `⨯ Error: aborted ... code: 'ECONNRESET'` lines a job log prints are another thing: the server noticing a browser that closed a request, minutes from the failing read.) The dev server's preload therefore requires `keep-alive-sockets.cjs` as well, which gives every server made with `http.createServer` (as `next dev` makes its own; `new http.Server()` and `https.createServer`, which `--experimental-https` would use, are not wrapped) `keepAliveTimeout = 0`: the server never closes an idle socket first, and a pooled one lasts until the server process ends. `next dev` takes no `--keepAliveTimeout` (only `next start` does), which is why the server is changed from the preload. `e2e-dev-server-keep-alive.test.ts` runs the sequence, a pooled socket written to while the server's loop is busy past its idle limit (scaled down to seconds), against a plain server, which must reset it, and against the preloaded one, which must not. A `read ECONNRESET` after this is another cause: look for the `Server is approaching the used memory threshold, restarting...` line first, a restart ending every socket.

## The window's width in a spec

Headless Chromium, as Playwright launches it (`--hide-scrollbars`), draws no scrollbar and gives it no room, so the root layout's pre-paint script finds none (`src/lib/scrollbar-room-restore.ts`), the root gets no `data-scrollbar-room` mark, and a page lays out across the whole viewport, as on a phone. A browser whose scrollbars take room (Windows, Linux, a Mac set to always show them) gets the mark and keeps that room open on every page (`html[data-scrollbar-room] { scrollbar-gutter: stable }`, design-web.md's "The scrollbar's room"), 15px narrower. `scrollbar-room.spec.ts` launches a browser of its own without `--hide-scrollbars` to draw that; a spec that should hold at both widths measures against `document.documentElement.clientWidth`, never `innerWidth`.

## Frames drawn from part of the HTML

Chrome's HTML parser stops on a time budget to let the page be drawn, whether or not the whole document is in, so a spec that records every frame from the document's first can see a part the parser has not finished: Generate with its attributes and none of its words, which failed `creator-arrival-steady.spec.ts` once on CI (2026-11-17). Nothing follows a part in the document until the parser has left it, so while `document.readyState` is `loading` a part with no next sibling on itself or any ancestor is unfinished. That spec leaves such frames out of its checks, with a bound on how long they stay on screen, `recipe-labels-viewer.spec.ts` takes a tile as drawn only once the parser has left it, and `refresh-layout-stability.spec.ts` records no frame while the parser is inside the top bar: six CI runs from 2026-11-15 to 11-23 failed its `rightX` check on a bar drawn without its search field or right-hand controls (183 to 757px off the final), the frame's `title`, `inviteY` and `balanceCard` showing the page not yet drawn. A spec that records every frame from the document's first needs the same rule.
