# E2E (Playwright) gotchas

Moved from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here. The fourth gotcha was added on 2026-10-20.

Four E2E gotchas worth knowing before you debug one:

- **Playwright's own dev server refuses to start if another `next dev` is already running**, even on a different port, and the failure reads as a config error. Stop any preview/dev server (including one started via `preview_start`) before `npm run test:e2e`.
- **The auth bypass needs its cookie, not just the env vars.** A spec that only visits an authenticated route lands on `/login`; add `{ name: 'e2e-auth', value: 'workflow-user', url: 'http://127.0.0.1:3100' }` via `context.addCookies` first (see the existing specs).
- **The dev server reloads an open page when another page connects after a compile.** `next dev --webpack` compiles a route the first time it is requested, and each compile gives the client build a new hash. Whenever any page opens its dev socket the server sends `sync`, with the current hash, to every open page, and a page that reads a hash other than the one it loaded with reloads itself — Next takes the change for a server restart (`next/dist/client/dev/hot-reloader/app/web-socket.js`; the hot update itself applies fine). Two pages and one first request are enough: one Playwright worker's test compiles a route, the next page to load reloads the page under the other worker's test, and whatever that test had typed or attached in memory is gone. CI therefore runs the suite on one worker (`playwright.config.ts`), which never has two pages open; a local run with several workers still meets it (`--workers=1` avoids it), and so would a spec that opens two pages. A self-reload landing in the same tick as a spec's own navigation cancels it, surfacing as `net::ERR_ABORTED; maybe frame was detached?`. `tests/e2e/kling-o3-named-subjects.spec.ts` carries the retry helper for it. On one worker a page cannot reload itself this way: it reloads only on a second `sync` (`mostRecentCompilationHash` in that file), and it gets one only when another page connects or its own socket reconnects.
- **A route's first request waits for the route's compile, and so does whatever waits on that request.** `next dev` compiles a route the first time it is requested, and again once it has dropped the route for sitting unused for 60 seconds (`onDemandEntries.maxInactiveAge`). When that request falls inside a wait with a timeout, such as a `toHaveURL` after a redirect, the compile is spent from that timeout. On this Mac `/login` compiles in about a second. On CI's runner it outlasted the 10-second `expect` timeout, and `workflow-builder.spec.ts`'s redirect test failed on one worker (Quality run 39339854631, 2026-10-19): `RequireAuth` redirects while `/create-workflow` streams, the browser's document request for `/login` waited behind that first compile, and the call log read `waiting for "…/login?returnUrl=…" navigation to finish`. The `[Fast Refresh] rebuilding` the page logs meanwhile is that compile starting, not a reload. In a trace (`0-trace.network`), a document request that never got a response points to a compile; a second load of the starting URL points to a reload. The fix is to request the route before the wait starts (`await request.get('/login')`, as that test now does). A retry or a longer timeout would only bet on the runner's speed. A `page.goto` has no timeout of its own, so a compile that lands inside one costs only test time.
