# E2E (Playwright) gotchas

Moved from `AGENTS.md` on 2026-10-18 so it loads only where it applies; the core file keeps a summary and points here.

Five E2E gotchas worth knowing before you debug one:

- **Playwright's own dev server cannot start beside another `next dev` of the same checkout**, even on a different port: Next allows one per checkout (the server process holds `.next/dev/lock` while it runs; `lsof -t .next/dev/lock` prints its PID), and the second prints "Another next dev server is already running" with that PID among Playwright's `[WebServer]` lines, then Playwright fails with "Process from config.webServer was not able to start". Stop this checkout's preview/dev server (including one started via `preview_start`) before `npm run test:e2e`; the local gate's `--e2e` names it and skips. A `next dev` of another worktree has a `.next` of its own and does not matter. Port 3100 must be free as well: the config never reuses a server already on it.
- **The auth bypass needs its cookie, not just the env vars.** A spec that only visits an authenticated route lands on `/login`; add `{ name: 'e2e-auth', value: 'workflow-user', url: 'http://127.0.0.1:3100' }` via `context.addCookies` first (see the existing specs).
- **The dev server reloads an open page when another page connects after a compile.** `next dev --webpack` compiles a route the first time it is requested, and each compile gives the client build a new hash. Whenever any page opens its dev socket the server sends `sync`, with the current hash, to every open page, and a page that has had a `sync` before reloads itself when the new one carries another hash — Next takes the change for a server restart (`mostRecentCompilationHash` in `next/dist/client/dev/hot-reloader/app/web-socket.js`; the hot update itself applies fine). Two pages and one first request are enough: one Playwright worker's test compiles a route, the next page to load reloads the page under the other worker's test, and whatever that test had typed or attached in memory is gone. `playwright.config.ts` therefore runs the suite on one worker, in CI and out of it, which never has two pages open; a run given `--workers` above 1 still meets it, and so would a spec that opens two pages. A self-reload landing in the same tick as a spec's own navigation cancels it, surfacing as `net::ERR_ABORTED; maybe frame was detached?`. `tests/e2e/kling-o3-named-subjects.spec.ts` carries the retry helper for it. A page gets a second `sync` only when another page connects or its own socket reconnects, so a single page on one worker does not reload this way; the dev client can still reload a page after a failed hot update or a runtime error, and a trace shows any reload as a second load of the page's URL.
- **A compile spends the timeout of whatever is waiting while it runs.** The E2E server, `next dev --webpack`, compiles a route on its first request, and again after dropping it (`onDemandEntries`: unused for 60 seconds and not among the last five pages a browser has had open; it goes at the next compile). While any compile runs, every compiled route counts as building, so a request for any route waits for it, not only the first request for its own. A step with no timeout of its own absorbs the wait (`page.goto` and `page.request` calls, while the config sets neither `navigationTimeout` nor `actionTimeout`); a timed wait such as `expect`'s 10 seconds spends it. On CI's one worker `workflow-builder.spec.ts`'s redirect test failed this way: the redirect from `/create-workflow` loads `/login` as a new document, the suite's first request for that route, and its compile outlasted `toHaveURL`. That test now asks for `/login` with `page.request.get('/login', { timeout: 0 })` right before the wait, so the wait holds only the redirect; a `beforeAll` or `globalSetup` warm-up comes too early, because the route is dropped again before the test runs. Warm with `page.request`, not the `request` fixture: it shares the page's cookies (the proxy routes `/` and `/home` by them) and its trace (the fixture's own log takes `0-trace.network` and pushes the page's to `1-`). A wait that also covers a slow server render, which no warm-up shortens, keeps a named longer timeout, as `COLD_PAGE` and `SLOW_PAGE` do. In a failed test's trace, a document request with neither a response nor a failure when the wait ended was still being served (compiled or rendered); `[Fast Refresh] rebuilding` in the console marks a page compile's browser half, after its server half, and an API route's compile logs nothing; a request that failed with `net::ERR_ABORTED` was cancelled, and a second load of the starting URL is a reload.
- **A compile that ends while a page hydrates can hold the hydration until the dev server has rendered the page again.** After a compile that changes a seen route's server layer or its CSS imports, the server sends every open page `serverComponentChanges`, and the dev client answers with `hmrRefresh()` (with a reload instead after a runtime error). The client opens its HMR socket before `hydrateRoot` (`next/dist/client/app-index.js`), and the router's dispatch exists from the hydration render on, so the refresh can reach the router before it has mounted. Its tree waits for the page's refetch (`?_rsc=`) for its segments' data, and the hydration then renders that tree, because the router mounts with the refreshed state. So the page stays the server's HTML until the dev server answers: 6.7 to 7.6 seconds on CI. Every check that HTML satisfies passes meanwhile. A press there is dropped, because React stops a discrete event on a root it cannot hydrate. A fill never reaches React's state, and the field's next render after the commit writes over its text; the creators' prompt boxes are the exception, which take in what was typed as they mount (`useTypedBeforeHydration`, held by `creator-prompt-before-script.spec.ts`). So a spec types or presses only after a sign that only the page's script gives. The signed-in creator specs (`creator-prices`, `creator-publish`, `creator-canvas`) wait for `Generate · 19 credits`; `creator-signed-out.spec.ts` waits for the page's first quote request (it failed this way on 2026-10-31). A `__reactFiber$` key is not such a sign. It shows only that the render reached that node, and a refresh that lands after that leaves the key on HTML React has not committed, so the key checks of four specs narrow this window without closing it: the `hydrated()` helpers of `alerts-signed-out-sheet`, `pages-open-at-top` and `public-page-after-signed-in-route`, and the inline one in `bottom-nav-overlays`. In a trace, look for three things in order: the console's "Can't perform a React state update on a component that hasn't mounted yet", then two `?_rsc=` requests, then the page's mount-time requests (the model catalog, `/api/app-version`), which start only after those requests are answered.

## The dev server's env

`playwright.config.ts` is the only source of the dev server's env, in CI as on a laptop (the E2E job sets none): the placeholder project and keys (`PLACEHOLDER_ENV`), the shell's env without any variable `.env.example` lists, and no `.env*` file of the checkout. Next would apply every key of those files that the server's env leaves unset, at start and on every forced env reload, which it does when an env file is saved and when a route is added or removed (a branch switch in that checkout too; `forceReload` in `setup-dev-bundler.js`, which logs nothing unless a file's text changed). So the dev server's preload, `tests/e2e/support/dev-server.cjs`, first requires `no-env-files.cjs`, which answers Next's `fs.statSync` and `fs.readFileSync` of those files at the checkout's root as if they did not exist. `npm run test:e2e` is therefore the job's run from any checkout with nothing exported, and the primary checkout's `.env.local` (production) never reaches the server. `e2e-smoke-readiness.test.ts` holds all three: every `process.env` name the app's code reads is listed in `.env.example` (a new one must be, or the test fails), a shell exporting all of them reaches nothing, and Next's own loader, at start and on a forced reload, applies a checkout's four files without the guard and none with it, also when the guard was required by a path in another case (Next resolves its directory with `realpathSync.native`, and so does the guard). To change a variable for a run, change `PLACEHOLDER_ENV`. The server also starts on an empty data cache: the config's command removes `.next/dev/cache/fetch-cache` first, because the checkout's own `next dev` keeps `unstable_cache` entries there under keys that do not name the project (the primary checkout's held production's feed for the signed-out `/showcase` on 2026-10-23), and Next serves such an entry stale when its refresh fails, as every refresh against the placeholder does.

## Pages that read Supabase on the server

The E2E run points the app at a placeholder project, `https://example.supabase.co`, a host with no DNS record, so every read the dev server makes fails and a page whose server render reads its data draws its error state; `page.route` answers only the browser. The dev server's preload (`tests/e2e/support/dev-server.cjs`, `NODE_OPTIONS --require` in `playwright.config.ts`) therefore also loads `tests/e2e/support/supabase-server-stub.cjs`. It answers the reads it lists, for the creator in `tests/e2e/fixtures/creator-profile.json` (the E2E user's page, `/creators/e2e-creator`; `creator-profile-editor.spec.ts` draws it), for the text post with a free recipe in `tests/e2e/fixtures/post-with-recipe.json` (its post page, by a creator of its own; `bottom-nav-overlays.spec.ts` draws it signed out), and for the E2E user's own image post in `tests/e2e/fixtures/post-composer-saved-twice.json` (its editor, `/post/e2e-composer-saved-twice/edit`; `post-composer-edit-saves-twice.spec.ts` draws it), and passes every other request on, so other pages fail offline as before. A spec that draws another such page adds that page's reads there, each matched by the filters that name its own fixture rows, never a whole table: the existing specs' pages made 78 server reads on 2026-10-23, `profiles?id=eq.workflow-user` among them, and a table answered with no rows would change what those pages draw. Two reads are answered without a fixture row, each because its answer draws the same as its failure did or what the creators' specs expect: the welcome grant (`credit_grant_programs`, `program_key=eq.welcome_credits_v1`: 25 credits, which the creators tell a signed-out visitor), and Pricing's referral terms (`referral_programs`, `status=eq.active`: no active program, which leaves the banner's numbers out as the failed read did, without the 9 seconds that read spent giving up on every Pricing a spec drew; 2026-11-02). `E2E_SUPABASE_STUB_LOG=<file>` writes one line per request, answered or passed on. Next's experimental test proxy (`experimental.testProxy`) answers server fetches per test instead, but this Next's docs do not describe it, and it is switched on only in `next.config.ts`.
