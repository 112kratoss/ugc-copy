# CDN audit — 10 September 2026

**Verdict: public media and public API caching work; anonymous page rendering, private-media cache policy, and monitoring need follow-up.** No CDN migration is justified by the measured evidence.

This is a fresh production and source audit, not a capacity certificate. It supersedes older CDN observations only for the surfaces and request shapes measured here.

### Public media: pass on every inventoried object

`showcase_media` is public and contains **119 objects / 152,648,711 bytes**. Every object's stored cache policy is `max-age=86400`.

| Sweep shape | Status | Served cache policy | Cache status |
| --- | --- | --- | --- |
| Ordinary GET, headers + first byte | 119/119 HTTP 200 | 119/119 `public, max-age=86400` | 64 HIT, 55 MISS |
| One-byte ranged GET | 119/119 HTTP 206 | 119/119 `max-age=86400` | 119 HIT |

The ranged request follows the ordinary GET for each object, so **119 ranged HITs are a warmed diagnostic result, not the organic traffic hit ratio**. No stale five-minute or one-year public-media header was observed. This rechecks the historical full-versus-ranged cache discrepancy documented in [the backfill verifier](../scripts/backfill-showcase-media-cache.ts).

The five complete sampled posters were 13,822–25,180 bytes and all ten requests were HITs. The selected original video reports 2,798,468 bytes; its corresponding feed rendition reports 465,804 bytes, **83.4% smaller**. Both served the requested 65,536-byte range, rather than the complete video. The sampled teaser also served a correct partial response. The avatar served a one-hour TTL. Sampled hashed JS/CSS warmed to HIT and advertise a one-year immutable browser cache.

### API boundaries: expected behavior in the tested cases

- Public recent feed, resources, templates and FX warm successfully even though the browser-visible header is just `Cache-Control: public`. Vercel consumes shared-cache directives; their absence in the downstream header is not a failure. [Vercel cache-control documentation](https://vercel.com/docs/headers/cache-control-headers)
- Web/mobile catalog URLs have distinct ETags. A conditional catalog request returned **304/HIT**; `refresh=1` returned **304/MISS with `no-store`**.
- An invalid bearer on the warmed recent-feed URL returned **401, `private, no-store`**, rather than the cached anonymous response. An unauthenticated private-media request also returned 401/no-store.
- Anonymous For You returned **200/MISS, `private, no-store`**, with a session cookie. Keeping a personalized response outside the shared cache is correct.
- A harmless cookie did not make the public recent feed private; it received a 270-second-old STALE entry, within the configured 60-second freshness plus 300-second stale window. This is a visible freshness tradeoff, not an unexpected cache failure.

These checks do not establish two-user authenticated isolation or expired-signed-URL revocation behavior.

## Findings and ordered follow-up

### CDN-1 — Medium: public discovery pages still require origin rendering

**Confirmed live and in current source.** Signed-out `/showcase` and `/marketplace` both returned `private, no-cache, no-store, max-age=0, must-revalidate` on all three fresh probes. API caches protect their underlying data, but the page response still requires server rendering for each navigation.

The shared [request-hinted auth boundary](../src/app/components/RouteAuthBoundary.tsx) calls `cookies()` before deciding whether auth exists. Both route layouts use it. The [Showcase page](../src/app/showcase/(feed)/page.tsx) and [Marketplace page](../src/app/marketplace/page.tsx) also await request `searchParams`. Marketplace's `revalidate = 60` does not make this whole request-dependent tree an ISR page. This agrees with the installed Next.js documentation on [request-dependent rendering](../node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md).

This is an origin-cost and latency opportunity, not a claim that the current no-store response is unsafe or accidental: Showcase explicitly documents its query-dynamic behavior. The earlier September 7 production run also recorded **147/147 MISSes for each page**, with Showcase P95 TTFB **1,652.8 ms**, over its 1,500 ms budget. That historical run used a different workflow SHA and is supporting history, not today's latency measurement.

**Follow-up:** give the default anonymous discovery views a cacheable shell and move viewer state/filter loading behind appropriate client or dynamic boundaries. Preserve authenticated behavior, query-specific metadata and crawlable content. Prove the resulting default public pages warm to HIT and that signed-in responses remain isolated. Setting a blanket public response header on the existing cookie-dependent tree is not an acceptable fix.

### CDN-2 — Medium: the production CSS improvement has not shipped

**Confirmed live; already addressed in the newer checkout, deployment pending.** Production still uses `experimental.inlineCss: true`; checkout [next.config.ts](../next.config.ts) disables it in commit `1864f2c`.

Fresh HTML contains **125,722 bytes of literal inline CSS** on each of Home, Showcase and Marketplace, and **318,933 bytes** on Blog. This stylesheet content travels inside each HTML response instead of being reused solely as a separate browser-cached resource. The deployed HTML bodies are 502–822 KB decoded on these surfaces. Showcase's fresh body is roughly **5.1% above** the configured 557,056-byte decoded budget, though this small audit sample is not a performance-harness P95 run.

**Follow-up:** validate and release the existing change through the normal Quality/protected release process, then remeasure live HTML, external stylesheet reuse and mobile LCP. Do not count the checkout's CSS savings as deployed savings. This audit made no release changes.

### CDN-3 — Medium: legacy private-media TTLs do not match the current policy

**Confirmed metadata drift; end-user revocation impact remains unmeasured.** Private `generated_images` contains **49** objects with `max-age=31536000`; private `generated_videos` contains **29**, totaling **78 objects / 15,887,213 bytes**. Of these, 63 are named as previews. Another 69 private generation objects carry a one-day TTL, while the remaining generation originals largely use one hour.

The public Showcase backfill did not normalize these private buckets. Current [generation preview uploads](../src/lib/generation-media-preview.ts) reuse the one-day Showcase constant, while [the private media route](../src/lib/media-read-service.ts) issues URLs valid for 600 seconds and [its redirect](../src/lib/media-route-adapter-service.ts) can be browser-cached for 60 seconds.

Signed URL lifetime and cached-object lifetime are separate controls. Supabase documents that a warmed signed URL can remain served for the object's cache duration after token expiry, and that deleting the object invalidates its entries. Metadata alone does not establish the actual served TTL on these private objects. [Supabase Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn)

**Follow-up:** define an explicit private-media retention/revocation policy, separate it from the public Showcase constant, and review the 78 legacy objects against it. If normalization is needed, verify actual responses through authorized Storage operations; SQL metadata updates alone previously failed to update public CDN headers. Acceptance should use an owner-authorized disposable asset, warm the URL, expire/revoke it, and check both fresh clients and client caches. No private asset was signed or downloaded during this audit, and no cross-user disclosure is claimed.

### CDN-4 — Medium: performance monitoring does not enforce CDN coverage

**Confirmed in the monitoring configuration.** [Performance budgets](../config/performance-budgets.json) enforce status, bytes and latency for five public targets, but none specifies an expected cache status. The harness supports cache-status enforcement, currently configured only for the origin profile. Its normal target list also omits direct Supabase media, video range semantics and Storage cache headers.

Consequently a fast run can pass while an intended cached surface becomes origin-bound. The September 7 run demonstrates the distinction: Marketplace recorded 147 MISSes without a target violation. The latest three listed performance runs all failed; the latest failed on Showcase and authenticated For You latency, while both Lighthouse jobs passed. [Latest inspected run](https://github.com/112kratoss/ugc-copy/actions/runs/34100497652)

**Follow-up:** add post-warmup HIT/STALE expectations or an explicit minimum hit ratio for targets intended to cache, with initial cold requests accounted for. Add a small durable-media canary that checks full/ranged status, content range and served TTL, plus no-store checks for personalized endpoints. Keep intentionally dynamic pages classified honestly until CDN-1 is addressed. Obtain a passing performance run tied to the newly deployed build; do not cite August's green baseline as current CDN certification.

## Additional limits and retained design tradeoffs

- The accepted public browser TTL is one day. A Storage delete cannot retract bytes already cached by a browser; the new sweep verifies delivery policy, not a live takedown. Moderation source includes original, poster, rendition and teaser paths in Storage removal, which is an important positive control.
- Next Image has its own cache. Its configured minimum TTL is one day, and remote patterns permit all Storage object paths, including signed paths. Generated hashed previews bypass this optimizer, but other images can use it. No optimized-copy takedown canary was performed. Include this extra cache in revocation testing before claiming that a Supabase deletion clears every delivered copy. [Next.js Image caching documentation](https://nextjs.org/docs/app/api-reference/components/image#minimumcachettl)
- Expo's image components use `memory-disk` caching and explicit cache keys. This audit did not test device eviction, logout cleanup or offline retention; the HTTP TTL must not be presented as a proven bound for native disk caches.
- Feed/marketplace invalidators use Next data-cache tags. Instant invalidation of every already-cached API response was not demonstrated. Keep the documented edge freshness/stale window in the acceptance criteria, or add a controlled invalidation test if a shorter guarantee is needed.
- No organic traffic logs, billed egress, per-country hit ratios, private signed-URL cache ratios, origin CPU utilization or sustained-load measurements were collected. The sweep's cache ratios cannot support a cost or MAU estimate. A second CDN would add operational complexity without resolving the source/configuration findings established here.

## Validation and reproducibility

Existing focused web checks passed: **12 files / 56 tests**, covering API headers, feed and marketplace cache policy, anonymous page components, private-media reads, preview URL handling, TTL migration and moderation operations. These are source checks on the checkout, not proof of deployed CDN behavior. A full build and broad app test run were unnecessary for report-only changes.

To repeat the audit: record `/api/app-version`; issue three identical ordinary GETs per HTTP target with cookies and authorization absent; record cache/status/age/vary/ETag/bytes/TTFB; inventory `storage.buckets` and `storage.objects` read-only; test every public Showcase path with ordinary and one-byte ranged GETs; repeat the private rejection and catalog conditional checks; record the ending build ID. Preserve public and personalized results separately and report the observer region. Use the checked-in evidence JSON as the exact request and expected-policy reference.

The all-object Storage probes deliberately consume only the first response byte. Full download integrity, rendered UI performance, post-deletion behavior and multi-region performance require separate checks.
