### 2. “Ready” did not guarantee readable bytes — high, data repaired

Generation `bbaf44f1-3633-4683-a4dd-eccd6d93f031` had a ready preview generated
on 12 August. Storage returned 154,737 bytes with a WebP signature, but sharp
could not decode them. The original image was intact. Re-encoding with the
current pipeline produced 85,312 bytes and the **same intended content hash**
already present in the old filename. This is consistent with the historical
binary/UTF-8 corruption documented in the repository; it does not establish
which historical writer made this particular object.

Repair jobs only select pending/failed/processing rows, so this ready row was
invisible to repair. A new `.repair-20260905.preview.<hash>.webp` object avoids
reusing the poisoned URL and mobile disk-cache key. The new file was compared
byte for byte, fully decoded, served through a fresh signed URL with HTTP 200,
and the generation pointer was conditionally updated. Original and old preview
remain available for rollback.

Native evidence: the production corrupt bytes failed in the actual Android
profile image component; the regenerated bytes rendered after changing the URL
and cache key. This controlled check temporarily substituted a local cache
entry, then restored it. It was **not** a recovery of the unrelated 404 post in
finding 1.

Prevention now in the checkout:

- Full byte equality on generation-preview readback, without another request.
- A read-only audit that actually decodes ready previews, rather than relying
  on database status or WebP magic bytes.

The post-preview writer still lacks the generation writer's readback assertion
(`src/lib/post-media-preview.ts`). All 21 existing post previews decoded in
this audit. Share the integrity check between both writers in the next pipeline
pass; no current post-preview corruption was observed.

### 4. URL expiry and recovery are not consistently propagated — medium, source finding

Generation responses sign owned URLs for one hour and advertise a 55-minute
deadline. Mobile copies that value to `previewExpiresAt`, but does not consume
it for media loading. The image retry control retries the same URL. Synthesized
post covers graft signed generation previews onto descriptors whose
`expiresAt` remains null (`src/lib/generation-preview-info.ts:101`).

The profile dashboard already refreshes stale queries on focus, and app
foreground state is wired to React Query; those are real mitigations. The
profile card feed nevertheless seeds `initialData` from other caches without
preserving their age (`ugc-mobile/components/profile-media-feed.tsx:103`).
This can temporarily treat older signed media as newly fetched.

This audit did not reproduce a naturally expired signed URL in the profile.
Do not present expiry as the proven cause of the user's intermittent black
frames. Next acceptance test: leave profile/viewer caches older than the URL
deadline, expire native image disk entries, then navigate and retry. Renewal
should be deduplicated per query/page and preserve a loaded poster while a
fresh URL arrives. It must not route native images through a cookie-only web
proxy or refresh every tile independently.

### 5. Private creations do not receive the public-post video optimization — medium

`owner-generations-route-service.ts:546` builds generation descriptors without
rendition/teaser URLs. The mobile viewer consequently uses the source for an
unpublished creation; its feed card can remain poster-only. The public post
pipeline has renditions, but that does not cover the entire profile library.

For the six post videos measured here, original objects total **83,312,375
bytes**, versus **7,960,183 bytes** for renditions: **90.4% smaller**. This is a
file-size comparison, not a measured session-egress reduction. Extend a private,
owner-scoped rendition pipeline before adding more autoplay. Preserve originals
for download; never publish private derivatives in a public bucket.

One 37.97-second post has a ready rendition but no teaser. The worker's normal
unresolved-rendition selection will not revisit a ready row solely to fill that
missing teaser. A bounded teaser-only backfill is the appropriate follow-up.

### 6. Failure recovery and decode size need a dedicated native pass — medium

Profile tiles use a dark background while images load. `StableMediaImage`
eventually shows retry after errors, but supplies no loading placeholder when
ThumbHash is absent. Video errors in `FeedVideoPreview`/the full viewer preserve
a usable poster when present; neither provides a complete URL-refresh/reload
path for every playback failure or an explicit bounded timeout for first-frame
arrival. These are source-level gaps, not confirmed decoder defects.

The 720px previews are already small: before repair, the readable sample had
median **27,828 bytes** and P95 **51,656 bytes**. A separate 256/384px grid
thumbnail can reduce transfer and decode memory further, but choose the size
from actual tile width and device pixel ratio. Coordinate with phase 5d of
`docs/plans/android-app-optimization-plan-2026-09-05.md`. Test fast scroll, background/
foreground, low connectivity, cold disk cache, and decoder pressure on physical
Android and iOS devices before attributing remaining black frames to rendering.

## Ready-video teaser repair — 2026-09-06

Reproduced a separate admission gap with a failing service test: ready full
renditions were never eligible for the repair sweep when only their teaser was
missing. Production had six ready published video renditions without teasers;
one exceeded the existing 30-second teaser threshold. Shorter videos do not
need this derivative under the current policy.

`post-media-teaser-repair.ts` now uses a separate service-only claim, lease and
three-attempt budget. It admits one existing rendition of at most 32 MiB from
the owning post prefix. Storage object metadata controls byte admission;
missing, malformed and oversized objects are excluded. Claims increment the
attempt count before encoding, so a killed worker cannot retry indefinitely.
Leases expire after five minutes. The worker runs only when the full-rendition
pass did no work, verifies uploaded bytes, and conditionally publishes against
both the current source and lease. It never sets a full rendition back to pending.
Older schemas degrade without disabling existing preview/rendition repairs.
Preflight is a cheap approximate metadata query; the claim makes the definitive
Storage-size/availability decision. An otherwise eligible missing/oversized
object can still cause an empty hourly sweep, but no download or encode.

Migration `20260905201219_repair_ready_video_teasers.sql` was generated through
the pinned CLI, captured from a local schema diff, and replayed from clean.
The diff omitted function ACLs, so explicit service-only grants are included.

recovery, crash attempt exhaustion and caller privileges. Worker tests cover

## Private creation playback baseline — 2026-09-06
