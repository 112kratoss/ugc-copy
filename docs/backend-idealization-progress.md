## Goal

Close the gap between a backend whose correctness core is strong and one that is also observable, behaviourally tested at the database layer, and structurally maintainable.

The v2 gates come from an independent audit of the code on 2026-07-25 rather than from a checklist review. That audit's verdict:

- **Near-ideal:** money-path correctness (atomic RPCs, hashed idempotency keys, refund-on-failure), security posture (170 RLS policies, owner-prefix signing, SSRF guards, fail-closed defaults), and release engineering (revision-guarded catalog releases, migration replay from clean in CI).
- **The gap:** observability, behavioural coverage of the credit-moving RPCs, and decomposition of the core generation modules.

Target architecture is unchanged from v1:

- Vercel is the API/business-logic boundary for both web and mobile.
- Supabase is the source of truth for Auth, Postgres, Storage, RLS, atomic RPCs, job locks, and durable state.
- Clients never own pricing, provider routing, credit settlement, payment trust, or generation validation.
- Expensive and failure-prone work is cached, rate-limited, idempotent, observable, and retry-safe.

## Completion Rule

An item is marked complete only when the current repo contains the implementation and there is relevant verification evidence. Production-only items remain open until the deployed environment is checked.

Use this convention:

- `~~completed item~~` means completed in the current local codebase.
- `in progress` means implementation exists but verification or cleanup is still ongoing.
- `open` means the work still needs to be implemented or audited.

A capability that exists but is not yet wired into a caller is **not** complete.

A gate may also close by an explicit, recorded decision not to build it. Workstream F closed that way on 2026-07-25: staying OAuth-only is a product choice, not an omission. Such closures state the decision and its consequences rather than implying the work was done.
